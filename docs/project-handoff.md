## Запуск и среда

Стек — React 19, Vite, обычные CSS и JSX, шрифт Inter, FastAPI, Pydantic, Uvicorn, SQLite и openpyxl. Для зависимостей используй `uv.lock` и `package-lock.json`. Python в проекте задан как `>=3.12`. В проверенной среде были Python 3.13.12 и Node.js 22.23.2.

```bash
cd /home/ruslan_safaev/sewing_factory
curl -fsS http://127.0.0.1:8096/api/health
```

Если сервер остановлен, подними его командой:

```bash
cd /home/ruslan_safaev/sewing_factory
./run.sh
```

Скрипт устанавливает зависимости из lock-файлов, собирает интерфейс в `dist/` и запускает Uvicorn на `127.0.0.1:8096`. Можно задать `FACTORY_PORT`. Uvicorn отдаёт и API, и готовый интерфейс, поэтому в обычном запуске нужен один процесс. Команда `npm run dev` запускает Vite для работы с интерфейсом. Запросы `/api` из Vite проксируются на локальный сервер на порту 8096 согласно `vite.config.js`.

Рабочая база лежит в `data/factory.sqlite3`. Её путь можно переопределить через `FACTORY_DB`. Начальное заполнение происходит при первом запуске базы и помечается через `settings.seeded`. Обычный перезапуск сохраняет накопленные записи. Для проверки операций с текущими исходными данными можно сделать согласованную SQLite-копию и запустить отдельный экземпляр после сборки:

```bash
cd /home/ruslan_safaev/sewing_factory
review_db=$(mktemp --suffix=.sqlite3)
REVIEW_DB="$review_db" .venv/bin/python - <<'PY'
import os
import sqlite3
from contextlib import closing

with closing(sqlite3.connect("file:data/factory.sqlite3?mode=ro", uri=True)) as source:
    with closing(sqlite3.connect(os.environ["REVIEW_DB"])) as target:
        source.backup(target)
PY
FACTORY_DB="$review_db" .venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8099
```

Открой интерфейс для таких проверок по адресу `http://localhost:8099/`. Рабочий SQLite использует WAL. Для резервной копии работающего приложения используй SQLite Backup API, как в примере. Файл базы и журналы находятся в `data/`. Сгенерированные `dist/`, `.venv/` и `node_modules/` восстанавливаются из исходников и lock-файлов.

## Учётные записи и права

Начальные локальные данные для входа перечислены в [README](../README.md#вход). Реальное состояние конкретной учётной записи определяется текущей базой, в том числе после смены пароля или переназначения склада.

| Роль | Начальный логин | Что доступно |
| --- | --- | --- |
| Администратор | `admin@factory.local` | Общие реестры, отчёты за смену, начисления, итоги месяца, каталог, сотрудники, остатки всех складов, поступления, отправки и сводка продаж. Создаёт региональные склады, назначает, меняет и отзывает доступ кладовщиков. |
| Бухгалтер | `oksana@factory.local` | Ведёт производственные отчёты, поступления и отправки. Работает с сотрудниками, спецификациями, начислениями, итогами месяца и сводкой продаж. |
| Мастер смены | `master@factory.local` | Обзор производства, создание и проведение отчётов, пять складов Иваново, просмотр изделий, спецификаций и карточек сотрудников. Расчёт работы виден в производственном документе. Персональные расчётные ведомости и общий раздел зарплаты предназначены для бухгалтера и администратора. |
| Кладовщик | `moscow@factory.local`, `petersburg@factory.local`, `yaroslavl@factory.local`, `nizhny@factory.local` | Остатки и история своего склада, приёмка адресованных ему отправок, оформление и печать местных продаж. |

Кладовщик аутентифицируется через `users`, его склад определяется текущим назначением в `grants`. Один аккаунт привязан к одному сотруднику и одному региональному складу. Назначение доступно действующему сотруднику с участком `warehouse`. При смене склада, отзыве доступа, деактивации сотрудника или переводе его участка с `warehouse` текущие сеансы этого аккаунта удаляются. При смене пароля сервер завершает прежние сеансы и создаёт новый (сохраняя текущий сеанс при смене из настроек). Региональный контур в API и UI получает только розничные цены без внутренней учётной себестоимости (`value`/`book_value`/`cost`).

UI показывает разделы по роли. Проверку действий выполняют `current_user`, `allow`, `document_scope` и `guard_document` на сервере. Вход выдаёт cookie `factory_session` со свойствами HttpOnly и SameSite Strict. Сервер хранит хеш токена и срок действия, а пароли хеширует через scrypt. Это конфигурация локального HTTP.

## Основные рабочие сценарии

### 1. Производство по фактической выработке

Бухгалтер или мастер переносит данные из журнала выработки. Каждый отчёт относится к одной дате, смене и этапу. В одном отчёте можно обработать несколько моделей и размеров. Строка привязана к конкретному SKU.

- **Выработка.** Выбрать изделие и записать количество комплектов.
- **Материалы и склад списания.** В отчёте можно выбрать «Склад списания сырья» (`source_id`, по умолчанию ID=1 «Склад сырья»; для `master` доступны только склады Иваново). Сервер рассчитывает норму на комплект, доступный остаток на выбранном складе и нужное количество по версии спецификации на дату отчёта. Предпросмотр выполняет тот же расчёт в откатываемом SQLite savepoint; при 0 материалах на этапе отчёт проводится без списания сырья.
- **Технологическая карта и зарплата.** Распределить комплекты между действующими исполнителями выбранного этапа. В черновике допустимо частичное распределение. Для проведения сумма распределений по каждой строке должна равняться её выработке.
- **Проведение.** Полуфабрикаты, материалы (с выбранного `source_id`), выпуск, расценки и история проходят одной транзакцией. При нехватке остатка или некорректном распределении запись остаётся в прежнем состоянии.
- **Исправление.** Бухгалтер или администратор указывает причину. Исходный отчёт получает статус `corrected`, его движения сторнируются, а связанный документ создаётся как новый черновик с сохранением исходного `source_id`. Проверки остатков действуют и для сторно. Если взаимосвязанные операции уже использовали запас, исправление может остановиться с ошибкой. Старый отчёт и его события сохраняются.

### 2. Цепочка из пяти складов в Иваново

| Этап | Что происходит при проведении |
| --- | --- |
| Раскрой | Со склада сырья списывается ткань по нормам. Крой приходуется на склад кроя. |
| Пошив | Списываются крой и сырьё, предусмотренное технологической картой этапа. Отшитые комплекты приходуются на склад пошива. |
| Упаковка | Поле передачи с пошива позволяет в том же документе перевести нужное количество на склад упаковки. Для выпуска списываются полуфабрикаты на складе упаковки и материалы упаковки. Готовые комплекты приходуются на склад готовой продукции. |

Внутренние склады имеют фиксированные ID 1–5 в `WAREHOUSES` в `app/db.py`. Для маршрутов, остатков и проводок эта карта критична. Остальные склады относятся к региональному контуру. Начальные города — Москва, Санкт-Петербург, Ярославль и Нижний Новгород.

### 3. Поступление сырья

Поставщик, номер накладной, дата, склад поступления (`target_id`, по умолчанию ID=1 «Склад сырья»), материалы, количество и стоимость за единицу. Кнопка «Добавить позицию» доступна без блокировки; прямо из формы поступления (и из редактора спецификации) администратор и бухгалтер могут создать новый материал через «+ Новый материал» (`POST /api/materials` с выбором единицы `м`/`шт.`/`кг`/`рул.`/`уп.`/`компл.` и автогенерацией `RAW-XXX`). Черновик можно сохранить и открыть позже. Проведение зачисляет сырьё на выбранный склад. Повтор того же номера накладной от того же поставщика блокируется при записи, включая различия регистра букв и внешних пробелов. Черновик и проведение используют один документ.

### 4. Перемещение и приёмка

Текущий маршрут — со склада готовой продукции в Иваново на выбранный региональный склад. Бухгалтер или администратор оформляет черновик и подтверждает отправку. При отправке количество списывается в Иваново, фактическая учётная стоимость фиксируется в строках, документ получает статус `in_transit`. Кладовщик склада назначения сверяет позиции и подтверждает получение. Приёмка увеличивает запас этого склада и переводит документ в `received`. Повторная отправка или приёмка не должна дублировать движения. Сумма в карточке перемещения и его реестре рассчитана по введённой цене строки, а приход запаса использует фактическую учётную стоимость, рассчитанную при списании. Эти суммы имеют разное назначение.

### 5. Продажа

Продажу оформляет региональный кладовщик (жёстко со своего склада) либо администратор/бухгалтер (со склада готовой продукции Иваново ID=5 по умолчанию или с выбранного регионального склада через `#/sales/new`). При выборе товара подставляется розничная цена SKU из каталога, которую можно отредактировать перед проведением (`price > 0` в строке); также можно добавить необязательный комментарий (`memo`), отображаемый в карточке `#/sales/:id` и печатной форме. Сервер списывает остаток и выдаёт документ о продаже. Печатная форма предназначена для внутреннего учёта. Интеграция с кассовым оборудованием потребует отдельной задачи.

Повтор запроса с тем же `request_key`, сотрудником и складом возвращает прежнюю продажу, если позиции, количества, цены, форма оплаты и комментарий совпали. Повтор с изменённым содержимым отклоняется (`409`). Работай с этим ключом при любых изменениях формы продажи.

### 6. Справочники, зарплата и итоги

- **Изделия.** Хранятся раздельные SKU по моделям и размерам. Спецификация версионируется, содержит сдельные расценки для раскроя, пошива и упаковки и гибкие нормы сырья (`0..120` позиций — на каждый этап можно задать `0`, `1` или несколько уникальных материалов, а также добавить новый материал прямо из формы). Новая версия действует с даты создания. Проведённые отчёты сохраняют ссылку, норму и расценку своей версии.
- **Сотрудники.** Есть карточка, должность, участок, дата приёма и статус. Бухгалтер и администратор могут смотреть историю выработки и начислений сотрудника и скачивать расчёт.
- **Зарплата.** Сдельное начисление считается по количеству и расценке из проведённых отчётов. Реестр поддерживает период, этап, поиск по сотруднику и Excel. Сумма относится к найденным записям.
- **Итоги месяца.** Вкладки «Выпуск и остатки» и «Себестоимость». Выгрузка включает два листа. Из строки склада можно открыть журнал операций за месяц. Себестоимость выпуска считается как НЗП на начало плюс материалы, сдельные начисления и прочие затраты минус НЗП на конец. Прочие затраты сейчас берутся из таблицы `overhead`.
- **Обзор.** Выбранная дата управляет выработкой и всеми отчётами за день (`day_reports`, включая черновики `day_drafts` и `draft_stages`). Если за выбранную дату есть непроведённые черновики, на экране показывается предупреждающий баннер с количеством комплектов и кнопкой перехода к проведению, а в списке «Требует внимания» черновики выбранной даты поднимаются наверх. НЗП на эту дату вычисляется из журнала движений. Полоса этапа ведёт в реестр со своими датой, этапом и статусом.

## Единицы, даты и смысл показателей

- В запросах количества передаются в натуральных единицах, цены — в рублях. В SQLite и числовых полях ответа количество хранится в тысячных единицы, денежные значения — в копейках. Например, `1250` у количества означает `1,250` единицы, а `1250` у суммы — `12,50 ₽`. На фронте используй `qty`, `money` и `number` из `web/ui.jsx`.
- Для материалов в метрах и килограммах (`м`, `кг`) допускаются три десятичных знака. Для изделий и штучных позиций (`шт.`, `рул.`, `уп.`, `компл.`) используются целые количества. Pydantic валидирует допустимые поля и точность, бизнес-проверки выполняются на сервере.
- Остаток по складу и SKU хранится в `balances`. История в `movements` содержит подписанные изменения количества и стоимости. Проводки и остаток обновляются вместе через `BEGIN IMMEDIATE`. Стоимость списания берётся пропорционально текущему количеству и оценке запаса, с округлением до копейки.
- Складские отчёты используют дату и время движения `movements.happened_at`, производственная выработка и зарплата — дату документа `documents.date`. Москва используется как часовой пояс. При доработке отчётности учитывай различие между датой документа и фактическим моментом проведения.
- Настройка `open_month` задаёт нижнюю границу периода для соответствующих операций. На момент передачи это `2026-11`. Эндпоинты отчётов, поступлений и отправки применяют текущие ограничения на дату. Интерфейс «Настройки» отображает открытый период.
- Поиск продаж работает на уровне документов. Если документ найден по одному изделию, в сводку и Excel попадает весь документ. Это важно при добавлении отдельной аналитики по SKU.

| Файл | Ответственность |

Основные связи в базе:

- `items` определяет позиции и SKU. `specs`, `norms` и `rates` хранят версии технологических карт.
- `documents` — заголовки операций. Префиксы документов — `ОС` для отчёта, `ПС` для поступления, `ПМ` для перемещения, `ПР` для продажи, `ОВ` для начальных остатков. `lines` — строки. `assignments` и `material_snapshots` фиксируют исполнителей, расценки и нормы. `source_doc` связывает исправление с исходным отчётом.
- `warehouses`, `balances` и `movements` связывают площадки, остатки и их историю. `events` хранит историю статусов, действий и причин по документам.
- `staff` — сотрудники, `users` — учётные записи, `grants` — привязки к региональным складам, `sessions` — активные сеансы.

Главные маршруты API:

- Идентификация — `POST /api/login`, `POST /api/logout`, `POST /api/password`, `GET /api/workspace`.
- Производство — `GET /api/overview`, `POST /api/reports`, `PUT /api/reports/{doc_id}`, `POST /api/reports/preview`, `POST /api/reports/{doc_id}/correct`. Сохранение и проведение различаются параметром `post`.
- Документы — `GET /api/documents/{kind}` и `GET /api/document/{doc_id}`. Реестр поддерживает `start`, `end`, `stage`, `status`, `warehouse`, `search`, `limit`, `offset` и `xlsx` там, где применимо.
- Остатки и операции склада — `GET /api/warehouses/{warehouse_id}`, `GET /api/warehouses/{warehouse_id}/movements`, `POST /api/warehouses`, `POST /api/receipts`, `PUT /api/receipts/{doc_id}`, `POST /api/transfers`, `PUT /api/transfers/{doc_id}`, `POST /api/transfers/{doc_id}/send` и `POST /api/transfers/{doc_id}/receive`.
- Складской доступ — `GET /api/access`, `PUT /api/access`, `DELETE /api/access/{staff_id}`.
- Продажи — `POST /api/sales`, `GET /api/sales-summary`, сводка и журнал используют общий фильтр.
- Справочники и отчётность — `/api/materials`, `/api/catalog`, `/api/catalog/{item_id}/versions`, `/api/staff`, `/api/staff/{staff_id}`, `/api/payroll`, `/api/month`. Точные методы и поля смотри в `app/main.py` и локальном OpenAPI по адресу `http://localhost:8096/openapi.json`.

## Что перенесено из Digital Platform

- Один поиск по журналу, учитывающий все страницы. Регистр букв и написание «е/ё» нормализуются. Поисковый запрос, фильтры и страница сохраняются при переходах внутри открытого интерфейса.
- Быстрые фильтры открываются отдельно, закрываются по клику вне панели (с учётом порталов), по `focusin` или через `Escape`. Очистка поиска и сброс фильтров выполняют разные действия. Активные критерии и период отображаются под поиском в виде кликабельных чипов со счётчиком выборки.
- Локализованный календарь `DateControl` (режимы даты и месяца) с быстрыми пресетами периода в `DateRange`, единая рамка таблицы со строкой итогов `tfoot`, состоянием `EmptyState` и пристыкованной пагинацией (`15/30/50`), 3-частный `Dialog` с фиксированными шапкой/футером, а также тосты `ToastProvider` / `useToast` при действиях и выгрузках.
- Excel относится ко всей отфильтрованной выборке. Имя файла понятно по названию реестра. Excel для продаж использует ту же область отбора, что сводка (включая разбивку по способам оплаты `payments`) и журнал, а экспорт текущих остатков следует поиску таблицы.
- Выбор сотрудника, изделия, материала и склада совмещён с поиском внутри одного поля (`SearchPicker` с поддержкой метаданных `meta` и подсветки совпадений). Есть выбор с клавиатуры. Вход, настройка доступа и смена пароля используют один компонент видимости пароля `PasswordInput`.

Хлебные крошки показывают контекст конкретного документа или карточки, а недоступные или несуществующие маршруты отображают явные экраны с возвратом на домашний раздел. ## Границы текущей реализации

- Основная производственная запись — фактический отчёт за смену. Планирование клиентских заказов, нормирование штрихкодами и работа операторов с телефона относятся к возможным отдельным задачам.
- Перемещения реализованы для маршрута Иваново → регион. Приёмка подтверждает весь документ, продажа списывается после подтверждения. Частичная приёмка, возвраты и корректировки продаж потребуют отдельных сценариев и складских правил.
- Розничная цена задаётся в карточке при создании SKU, нормы и расценки меняются выпуском версии спецификации. Управление открытием и закрытием периода и ввод прочих затрат через UI потребуют отдельных изменений.
- Вход работает через существующие или назначенные администратором локальные аккаунты. Кнопка «Не помню пароль» показывает инструкцию обратиться к администратору. Для восстановления пароля как автоматического процесса нужно отдельное решение.
- Схема создаётся через `SCHEMA`. При следующем изменении структуры базы понадобится явный совместимый переход для существующего файла. Учитывай историю проведённых документов.
- Перед подключением внешних сервисов или публикацией нужна отдельная задача с выбранной схемой доступа, хранением данных и порядком резервного копирования.
